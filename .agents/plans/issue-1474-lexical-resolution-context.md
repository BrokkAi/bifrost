## Purpose / Big Picture

Today Bifrost can tell you *what* an identifier occurrence resolved to (the #1473 occurrence row carries `OccurrenceTarget`), but it cannot tell you *why* — or why not. The resolver considers candidates in a precedence order (local binding beats member, member beats import, import beats package), rejects losers by shadowing, namespace, visibility, or position, and then throws all of that away: precedence is statement order inside fourteen per-language resolver files, a rejected candidate is a `continue`, and the only surviving trace is a free-text diagnostic string on the whole outcome. The 53 mined regressions in the issue inventory share one shape: the resolver picked the wrong candidate, or rejected the right one, and nothing queryable could have expressed the invariant "the selected target is the unique highest-precedence applicable candidate here."

There is a second, concrete motivation recorded in the issue comments: running the built-in `bifrost.code-smells` pack against this repository produced 284 findings with a 100% false-positive rate, and roughly 250 of them reduce to one missing predicate — *is the value operated on inside this loop declared inside or outside the loop body?* That is a reaching-binding question: join the receiver occurrence to the binding that is actually in effect at that position, then ask whether that binding's declaring scope is contained in the loop. Neither "the reaching binding of an occurrence" nor "the declaring scope of a binding" exists as data today.

After this change, four things work that do not work today:

1. RQL can enumerate the lexical environment as typed rows. A query can list the lexical scopes of a file (each with a stable AST identity and a parent), the bindings each scope introduces (locals, parameters, pattern binders, imports — each with the byte interval in which it is in effect and its hoisting behavior), and the package/module clause a file belongs to. The same rows appear in canonical CodeQuery JSON.
2. An identifier occurrence can be joined to its *reaching binding*: the specific binding of that name that is in effect at that exact source position, computed from activation intervals and scope ancestry rather than from source-order co-presence. From the binding, one more step reaches its declaring scope, so "receiver declared outside the enclosing loop" becomes a two-step structural query.
3. Reference-class occurrences expose *resolution candidate rows*: for a supported occurrence, the set of candidates the resolver considered, each with a precedence tier (a small language-neutral vocabulary: lexical binding, own member, inherited member, explicit import, wildcard import, same package/module, external, and so on), an outcome (selected, or rejected with a typed reason such as shadowed, wrong namespace, not visible, not in scope at this position), and a boundary status (whether resolution crossed an authoritative boundary such as an unindexed external root). Where a language's resolver has not been instrumented, the candidate query reports incomplete — never an empty complete answer.
4. The RQLP `assertion` analysis kind (from #1473) gains resolution asserts: a policy can require that the selected target of an occurrence sits at (or above) a given precedence tier, forbid selection from a given tier (the "no name-only fallback past an authoritative boundary" contract), and require or forbid reaching-binding containment relative to the subject capture (the loop-invariance predicate). Incomplete inputs yield `unreliable`/`Inconclusive`, never a clean pass.

Observability: after the final milestone, `cargo nextest run` shows environment and candidate queries returning classified rows in the four deep languages (Java, Rust, Python, JS/TS); the policy CLI runs a resolution assertion that fails on a seeded shadowing fixture and passes on its near-miss; and a fixture-level prototype of the "sort in loop over a loop-invariant binding" rule separates the true-positive shape (`crates/bifrost-policy/src/composition/precedence.rs`-style: binding declared outside the `while`, sorted each iteration) from the dominant false-positive shape (loop-local binding sorted once per iteration).

## Surprises & Discoveries

Findings from the pre-plan surveys (2026-08-04). Update this section as implementation proceeds.

- Observation: precedence is nowhere a value. The Java bare-identifier path (`crates/bifrost-analysis/src/analyzer/usages/get_definition/java.rs:1282-1349`) encodes "file-local type > local binding gate > member > static import > boundary" purely as statement order with early returns. The same is true across all fourteen `get_definition/*.rs` files (~54k lines total). Rejection sites (`LocalInferenceEngine::is_shadowed`, `rust::lexical_scope::name_shadowed_in_tree`, `python_name_shadowed_at`, Go's `shadowed: bool`) discard the losing candidate; the only surviving record is the untyped `DefinitionLookupDiagnostic { kind: String, message: String }` (`get_definition/mod.rs:447`), and navigation post-processing rewrites even that (`mod.rs:1455, 1512, 1528, 1548`).
- Observation: the exact join point for candidate rows already exists. `occurrence_rows.rs:379` zips reference-class occurrence rows with `DefinitionLookupOutcome`s and collapses each outcome to `OccurrenceTarget`, dropping `diagnostics` and everything the resolver knew. Candidate rows hang off this same zip.
- Observation: activation intervals exist as data in exactly two languages, in different shapes, both private and boolean-query-only. Rust: `RustLexicalScopeIndex` (`rust/lexical_scope.rs:474`) with `BindingVisibility { start, end, function }` — `let` bindings run from declaration end to scope end (`:514`), `match` arm bindings from pattern end to arm end (`:532`), items get the whole scope (hoisted, `:668`). Ruby: `LocalBindingTimeline` (`ruby/semantic.rs:239`) with per-name activation offsets. JS/TS deliberately drops order (`JsTsLexicalBindingIndex`, `js_ts/syntax.rs:120-131` — `var` hoists, lexical declarations are treated scope-wide). Python is function-scope categorical (`PythonLexicalScopeInventory::name_resolution_at`, `python/bindings.rs:329`) except comprehension targets, which are range-scoped.
- Observation: no language builds a parent-linked lexical scope tree. Rust and JS/TS build flat name-to-interval maps; everyone else re-walks tree-sitter ancestors per query through the shared grammar tables in `analyzer/lexical_definitions.rs` (`is_lexical_scope` at `:1147`, `is_parameter_owner` at `:886`, etc., all eleven languages covered). The only parent-linked scopes in the repo are CFG completion frames (`semantic/cfg.rs:715-780`), which are control-flow targets, not binding environments.
- Observation: the reaching-binding answer is computed and immediately discarded today. `resolve_lexical_binding` (`lexical_definitions.rs:259`) walks ancestors outward and, when a plain local wins, returns `LexicalBindingResolution::OtherLocal` — deliberately opaque, "a nearer local wins" without saying which. `get_definition/mod.rs:1147-1155` turns that into `no_definition("local_binding")`. This is also the root cause of follow-up issue #1569 (Java bare local reads resolve `NoDefinition`): the winner's identity exists at the moment of the walk and is thrown away.
- Observation: `StructuredImportPath` (`bifrost-core/src/analyzer/model.rs:2560`) already carries `lexical_prefixes`, `lexical_scopes` (byte ranges), and `declaration_start_byte` — import activation intervals exist as parsed data. Only Scala consumes them positionally (`scala_import_visible_at`, `scala/wildcard_imports.rs:202`). Python's `PythonImportBinding` (`python/imports.rs:124`) carries `start_byte, scope_start_byte, scope_end_byte` explicitly.
- Observation: Scala has a working precedence/ambiguity prototype, confined to Scala and `pub(crate)`: `ScalaWildcardImportEnvironment { owners, ambiguous: bool }` with ordered owners, and `ScalaExplicitImportTier { candidate, declaration, package }` (`scala/wildcard_imports.rs:45, :57`). It is the design template for the tier vocabulary, but Scala's occurrence adapter is all-`Unsupported` (the #1473 rollout stopped at four deep adapters), so Scala cannot be a claimed language here without first graduating its occurrence support.
- Observation: wildcard-import ambiguity is a first-class value only in Scala. Java silently returns `None` when two wildcard packages collide on a simple name (`java/imports.rs:637-646`); Python skips `from x import *` entirely when building binding rows (`python/imports.rs:186`); Rust and JS/TS track nothing. "Unresolved wildcard ambiguity as incomplete evidence" (an issue requirement) has exactly one precedent to generalize.
- Observation: `DefinitionLookupStatus::UnresolvableImportBoundary` is one undifferentiated bucket, and `semantic/workspace_oracle/dispatch.rs:678` classifies it as `DispatchQuality::Complete`. It cannot distinguish "external root exists, declared in the build, but unindexed" from "nothing known". The JVM external index tracks its own truncation (`MAX_INDEX_ARTIFACTS` etc., `jvm/external.rs:42-50`) but its `production_diagnostics` are `#[cfg(test)]`-only. Semantic-pack inventory evidence (`semantic_model/authoring.rs:761-895`, commit `81f536ba3`) is the closest existing "external root identity plus availability" row.
- Observation: no normalized visibility model exists for workspace source. `CodeUnit` has no visibility field; the typed `Visibility` enum (`semantic_model/model.rs:350`) covers external artifact facts only; Rust's `RustVisibility`/`Domain` (`rust/imports.rs:12`, `rust/usage_index.rs:230`) is the most developed model and is really name-resolution reachability; Java and PHP do string modifier matching.
- Observation: loop containment is ready-made. `NormalizedKind::{Loop, ForLoop, WhileLoop}` with subsumption exist and are mapped in all deep adapters; the facts arena is pre-order with `subtree_end`, so ancestor checks are O(1) (`FileFacts::is_ancestor`, `structural/facts.rs:587`). The missing half of the loop-invariance rule is binding identity, not loop structure.
- Observation (M1): the facts snapshot version was already 3 on this branch, not 2 as the plan text assumed. `#1473` merged with a note that version 2 had been claimed twice on divergent branches (loop-kind refinement and the occurrence-role rows), so their merge took 3. The `Block` bump is therefore 3 -> 4, and the plan's "2 -> 3" wording is superseded.
  Evidence: `crates/bifrost-analysis/src/analyzer/structural/facts.rs:29` before the change read `STRUCTURAL_FACTS_SNAPSHOT_VERSION: i64 = 3` with that comment.
- Observation (M1): `Block` does not change the snapshot's binary shape, only what extraction produces. A version-3 payload still decodes; it simply describes an arena in which no statement list is a node. The version key is the entire protection, which is what the new `pre_block_payloads_decode_and_are_therefore_gated_by_the_version_key` test in `facts.rs` states, rather than the wire-shape rejection #1473 could assert.
- Observation (M1): adding `Block` broke Python method refinement, and the fix is a design improvement rather than a workaround. `PythonStructuralSpec::refine_kind` decided "this `def` is a method" from `enclosing`, the nearest enclosing *normalized* kind, which used to be `Class`; with the suite normalized, the nearest normalized ancestor became `Block`. Five cross-language tests failed on this one cause.
  Evidence: `structural_search_python::decorated_functions_and_method_kind_refinement` reported `left: 0, right: 2` for the method query before the fix; the full `suite_cross_language` run is green after it.

- Observation (M1): the shared kind vocabulary has three consumers a new kind must be added to at once, none of them obvious from the registry: the two TextMate grammars (`editors/vscode/syntaxes/bifrost-rune-ir.tmLanguage.json` asserted by a `bifrost-core` unit test, and `bifrost-rql.tmLanguage.json`), and the executable tutorials, where `tutorials_cover_all_public_kinds_roles_and_pages` requires a positive, executed query for every public kind. `block` therefore ships with a worked Java example whose expected output is real tool output.
- Observation (M1): the four deep adapters needed no new grammar knowledge for blocks; `analyzer/lexical_definitions.rs::is_lexical_scope` already named exactly the node kinds mapped here (`block`/`switch_block`, `block`, `block`, `statement_block`/`switch_body`).
- Observation (M2): the Java adapter records no parser-derived import path at all. `java::imports::parse_import_info` builds its `ImportInfo` by trimming the raw snippet and sets `path: None`, so an import binder row can name the local name but cannot state the target segments, the declaration start byte, or the lexical scope. Rather than reconstructing the target from the snippet (which the repository's design philosophy forbids), the environment result reports the `ImportBinders` axis incomplete with a new `ImportTargetUnstructured` reason while the row itself still exists. Milestone 3's `ExplicitImport`/`WildcardImport` tiers therefore cannot name a Java import's target from this layer alone; populating `StructuredImportPath` in the Java adapter is the fix and is worth its own follow-up.
  Evidence: `crates/bifrost-analysis/src/analyzer/java/imports.rs:699-720`; the assertion in `java_import_and_local_rows_coexist_with_their_own_intervals` pins the incompleteness rather than an empty target.
- Observation (M2): Python contributes no local bindings, by construction in two independent places. Its occurrence classifier does not give an assignment target the `Binder` role (`python/structural.rs:130-145` lists parameters, patterns and for-clauses only), and the shared grammar table's `is_local_declaration` returns `false` for Python because "assignment in Python/PHP/Ruby may merely rebind an existing parameter". Python's binding rows are therefore parameters, comprehension and loop targets, and `as` patterns; there is no Python analogue of #1569 shape 1, which is why the regression test covers Java, Rust, JavaScript and TypeScript only.
- Observation (M2): Java's enhanced-for variable is not a binder occurrence. `JAVA_BINDER_HEADS` (`java/structural.rs:155`) does not include `enhanced_for_statement`, whose `name` field declares the loop variable, so `for (String row : rows)` produces no binding row. This is an occurrence-classification gap inherited from #1473, not an environment gap; the acceptance fixture uses a classic `for` with a body-block local instead. Adding the head is a one-line adapter change whose blast radius is occurrence rows, so it belongs to a separate change.
- Observation (M2): the `OtherLocal` fix moved 27 fixtures across five suites, and every one of them became a stronger assertion rather than a weaker one. Nineteen in `suite_symbols` (per-language "local value returns no definition" tests, a Java local shadowing two same-named fields, a Rust local shadowing a glob import, JavaScript hoisted declarations, TypeScript for-of bindings, the Kotlin abstention contract), four in `suite_analyzers` (three Scala precedence tests and a C++ local lambda shadowing a member), one in `suite_cross_language` (the Java occurrence conformance scenario's shadowing read moves from `unresolved` to `lexical`), two in `suite_mcp_cli` (both LSP click-around fixtures gained a marker for the binder they now jump to), and one in the analysis lib's MCP-parity test.
  Evidence: `suite_symbols` reported `1175 passed; 19 failed` before the fixture updates and `1194 passed; 0 failed` after.
- Observation (M2): on the by-reference surface the fix *sharpens* an existing diagnostic instead of changing a status. `render_definition_reference_lookup` (`searchtools/definitions.rs:285`) already answered `local_binding_requires_location` whenever an outcome carried a lexical definition; it simply never saw one for a plain local. Two tests that pinned `local_binding` now pin the sharper reason, and the status stays `no_definition` because a symbol name without a source position genuinely cannot address a lexical binding.
- Observation (M2): the mapping from an arena node back to a tree-sitter node is a byte-range lookup, and that is not a range coincidence. The environment producer re-parses the exact source the facts snapshot carries (`FileFacts::source`, whose `ContentIdentity` addresses every row), so `descendant_for_byte_range` over that tree is an inverse of the extraction walk rather than a heuristic match. The alternative -- carrying tree nodes through the facts arena -- would defeat the point of the arena.
- Observation (M3): the three shared outcome constructors cannot take a sink parameter. `candidates_outcome`, `lexical_definition_outcome` and `gated_boundary` are free functions with 304 call sites across the fourteen `get_definition/*.rs` modules *and* the unrelated `get_type` family, none of which reason about tracing. The sink is therefore a thread-local recorder installed by a `TraceSession` guard for one batch and drained at the per-request boundary; an untraced resolution pays one thread-local read per constructed outcome and allocates nothing.
  Evidence: `grep -rn "candidates_outcome\|lexical_definition_outcome\|gated_boundary" crates/bifrost-analysis/src/` reports 304 lines, 76 of them in `scala.rs` alone.
- Observation (M3): the shared seams cannot always name a tier, and inventing one would be worse than admitting it. `lexical_definition_outcome` knows its tier by construction (a lexical binding *is* `LexicalBinding`) and `gated_boundary` knows `ExternalRoot`, but `candidates_outcome` receives a bare `Vec<CodeUnit>` from any of fourteen resolvers and has no way to know which tier produced it. `TraceCandidate::tier` is therefore `Option<PrecedenceTier>`, deviating from the plan's unconditional field: `None` means unattributed, never "weakest", so a Milestone 5 tier comparison over an unattributed row must be inconclusive rather than a pass or a violation.
- Observation (M3): tier attribution had to be staged rather than scoped. A resolver tier knows its tier several call frames above the constructor that mints the row, and Rust's match arms return their candidates before any guard could span the constructor. The recorder therefore carries one *staged* `(tier, fq_names)`, and `candidates_outcome` spends it only on an outcome that reports one of those names; a staged tier that does not match is dropped, so a tier staged for a receiver-type lookup can never be spent on the reference's own answer.
- Observation (M3): the same guard was needed a second time, in the opposite direction. `java::imports::resolve_type_name_with` is the canonical explicit-import > wildcard-import > same-package ladder, but it also runs for receiver types and owners on the way to an answer. Staging is therefore gated on a `DeepScope` naming the reference the traced resolver path is currently resolving, opened once at each language's dispatch entry (`resolve_java_in_session`, `resolve_rust`) rather than in the bare-identifier path, because a Java return-type reference never reaches `resolve_java_bare_identifier`.
  Evidence: the first version of `an_explicit_java_import_selects_over_the_wildcard_routes_it_beat` reported `tier: None` for the selected unit until the scope moved up to the dispatch entry.
- Observation (M3): the resolver computes no rejected candidate for the shadowing case, because it stops at the winner. `resolve_lexical_binding` walks scopes outward and returns on the first match, so the outer binder it passed is never materialized; the Rust and Java `locally_bound` gates likewise *prevent* the losing lookup rather than performing it. The shadowed rows therefore come from Milestone 2's `reaching_binding`, whose `Shadowed { winner, shadowed }` is the same derivation asked for the whole answer, and they are attached only when its winner is the binder the resolver actually selected. That check is what keeps the join a producer consulting a producer rather than a second opinion.
- Observation (M3): two of the rejection reasons the plan named have no computed site in the instrumented paths. Nothing in `get_definition/java.rs` or `get_definition/rust.rs` discards a candidate on a visibility modifier (`NotVisible`), and `RustSymbolNamespace::accepts` does not exist -- `RustSymbolNamespace` is confined to `rust/usage_index.rs`, which serves `scan_usages`, not definition resolution. The namespace rejection that does exist is `rust_role_accepts_scoped`, a role filter over computed scoped candidates, and that is what `WrongNamespace` is emitted from. No new check was added to manufacture the others.
- Observation (M3): dependency-discovery evidence is not available to a query. `resolve_python_semantic_pack_dependencies` and its JS/TS sibling are caller-driven filesystem walks whose `DependencyDiscoveryOutcome` is not retained on the analyzer, so consulting them from a resolution trace would make a code query do package-manager work. The Python/JS-TS boundary refinement therefore reads the activated semantic-model overlay, which is real evidence the analyzer already holds, and reports `ExternalUnknown` where there is none.
- Observation: `Namespace` was already promoted to `bifrost-core` by #1473 with a recorded note that the Rust-internal `RustSymbolNamespace` "stays where it is until the resolver work in #1474/#1475". Java and Rust classify `PathSegment` occurrences but drop every row for lack of a namespace (`NamespaceUnknown(path_segment)`), because module-vs-type is undecidable at the token in those grammars.

- Observation (M4): the three runtime exhaustiveness assertions #1473 warned about fired again, exactly as predicted, and nothing else did. `assert_detailed_terminal_identities` and the `detailed CodeQuery domain and typed key must agree` assertion in `results.rs` are `assert!`s over tuple patterns rather than `match` arms, so the compiler said nothing and the first end-to-end run panicked in all ten new tests at once. The transferable instruction is the one #1473 already wrote down: grep `assert_detailed_terminal_identities` before running a suite after adding a domain. It is worth repeating because following it would have cost one minute and not following it cost a full test run.
  Evidence: `panicked at crates/bifrost-analysis/src/analyzer/structural/search/results.rs:2514: detailed CodeQuery domain and typed key must agree`.
- Observation (M4): the `json_fields!` registry cannot hold two fields with the same JSON label, and the scope and binding filters both want `kind`. The macro generates `from_label` as a literal `match`, so a duplicate label is an unreachable arm (a `-D warnings` failure) and a silently wrong `from_label`. Renaming one of them to something an author would not guess was the wrong fix; the scope axis got its own one-entry registry, `ScopeFilterField`, instead. A future filter family whose JSON keys collide with an existing one must do the same rather than renaming.
- Observation (M4): `reaching-binding` does not take a `:name` filter and must not. The step's whole meaning is "the binding of *this occurrence's* name", so a name filter on it would either be redundant (the name matches by construction) or contradictory (a filter that can never match). The end-to-end discriminator therefore filters the resulting binding rows by name, which is where the name is a control variable rather than an input. The first version of the test passed `"name": ["rows"]` to the step and was correctly rejected at decode time with the field path `steps[0].name`.
- Observation (M4): the file row's package fields had to appear and disappear together, and finding that out was a documentation failure rather than a code one. `PackageClauseRow::syntactic` is a per-language constant, so a file with no package at all still reports `syntactic: false` -- which on the wire would have read as "this file's package is derived from its path", a claim about a package that does not exist. `package_syntactic` is therefore emitted only when `package_fq` is, and both the Rust doc comment and the Python model say why.
- Observation (M4): two documented tutorial pages carry file rows in their expected output, so the package clause was not additive to the docs even though it is additive to the wire shape. `code_query_tutorials` compares documented JSON against real tool output, so `set-composition.md` and `reference-traversal.md` both moved. That is the executable-docs contract working: a published shape changed and exactly the pages that publish it failed.
- Observation (M4): candidate rows need their own per-file derivation, and reusing the occurrence cache would have been a real cost regression. `occurrences_for_file_with_options(..., WITH_CANDIDATES, ...)` runs a full resolution batch with a trace sink attached; the plain `ROWS_ONLY` derivation the occurrence domain already caches does not. The two therefore live in separate maps on the environment cache, keyed by file, so a query that never says `candidates-of` never pays for a trace.

- Observation (M5): the `reaching-binding` step's answer was unjoinable, and no consumer had noticed because no consumer had correlated it yet. A binding row named the binding but not the occurrence it was the reaching binding *of*, so a policy that captured one token could not tell which of several returned bindings was its own; and two occurrences reaching one binding deduped to a single row, erasing the second answer. `CodeQueryBinding::reached_from_ast_id` and its place in the dedup key are the fix. The transferable rule is #1473's, applied one layer later: a derived answer about an occurrence must carry that occurrence's identity, or the derivation is a dead end for exactly the correlated consumer it was built for.
  Evidence: the Java loop fixture returns two identical `Collections` import-binder rows after the change and returned one before it.
- Observation (M5): capability reporting decides the shape of the authored form. Defaulting the candidate seed to "every reference-class role" would have made a Java or Rust run unreliable the moment a file contained a path segment whose namespace the adapter cannot name (`NamespaceUnknown(path_segment)` is reported through `OccurrenceRoleUnsupported` with `Incomplete` impact whenever the role is in `required_roles`). An unrelated adapter gap would then have decided an unrelated verdict. Every new assert family therefore carries a required `:role`, exactly as `(assert ...)` does, and narrowing is the reason rather than symmetry.
- Observation (M5): an assert about how a token resolves does not apply to a token that is not an occurrence of its role. The first version of the tier assert reported `Inconclusive` on the Rust shadowing fixture because the subject selector `(identifier :text/regex "^value$")` captures two `let` binders as well as the read, and the binders have no candidate rows. Fetching the occurrence rows for *every* family, not only the occurrence family, is what makes "this assert does not apply here" distinguishable from "the resolver recorded no trace"; the first is silence and the second is inconclusive.
  Evidence: the run reported `Inconclusive { reasons: [CapabilityIncomplete] }` with the message "an assertion could not conclude over the rows the analyzer could state" before the applicability check, and `Complete` with zero findings after it.
- Observation (M5): `assert-boundary` and `assert-resolution` need opposite rules for an empty selection, and the Java `Collections.sort` receiver is the case that shows it. - Decision (M5): the canonical projection tags *every* assert with its `kind`, including the occurrence family that was previously untagged. An untagged projection would let two documents with different record heads project the same object the moment a future family happened to share a field set, and the semantic hash is exactly what that would silently collapse. No built-in policy authors an assertion, so no built-in semantic hash moved; the single checked-in authored gold (`tests/fixtures/policies/role-fidelity.normalized.json`) was updated in the same commit, and `checked_in_catalog_is_internally_consistent` and `builtin_policy_pack` both pass unchanged.
  Rationale: an injective projection by construction rather than by luck.
  Date/Author: 2026-08-04, Fable 5.
- Decision (M5): a reference with no reaching binding is a *complete negative*, not an incomplete input, so a containment assert over it is skipped rather than reported. "No binding of this name is in effect here" means the name resolves to something other than a lexical binding, and there is no declaring scope for a containment requirement to constrain. An environment that could not state its intervals is a different case entirely and has already made the run inconclusive through the query's own `environment_derivation_incomplete` diagnostic. Treating the two the same would have made every field receiver make the whole run inconclusive, which is the loop-invariance rule's most common shape.
  Rationale: the honesty spine already distinguishes them; do not re-decide it in the consumer.
  Date/Author: 2026-08-04, Fable 5.
- Decision (M5): containment is compared as display regions of two nodes of one file, not as a scope-index ancestry walk. A capture carries a `range` but no byte span, and requiring the second capture to *be* a scope-forming node would have refused the general case the plan asked for ("a second named capture's node interval"). Both regions address arena nodes of the same file, so the comparison is node containment expressed in the only coordinate system both sides publish -- the same comparison the Milestone 4 end-to-end discriminator makes.
  Rationale: answer the general question rather than the convenient one.
  Date/Author: 2026-08-04, Fable 5.
- Decision (M5): a violated resolution or boundary assert publishes one related location per considered candidate, and every candidate row that is not unit-backed resolves to the *reference's* own span. A candidate row carries the reference's span by construction and a unit-backed candidate's declaration carries no byte span, so the only distinct location available is the declaration's file, which unit-backed candidates use as an artifact-only location. The candidate detail a reader actually needs -- which tier was selected, and what was observed -- is in the typed evidence's `expectation` and `observed` fields rather than in a location.
  Rationale: publish the count and the ordering truthfully, and put the detail where it can be read.
  Date/Author: 2026-08-04, Fable 5.
- Decision (M5): `AssertionFindingEvidence` gained `assert_kind` and generalized `expected_cardinality` into `expectation` plus an optional `observed`, rather than growing a per-family evidence variant. The four families differ in what they compare, not in what a reader needs: a statement of the requirement, a statement of the observation, and the anchor. One evidence type keeps the renderer parity claim single, which is the same argument that kept the analysis kind single.
  Rationale: one shape per finding kind, not one per predicate.
  Date/Author: 2026-08-04, Fable 5.
- Decision (M5): `reaching-binding` output rows carry `reached_from_ast_id` and it is part of the dedup key, so one binding reached from two occurrences is two rows. The alternative -- leaving the step's answer unjoinable -- would have forced the policy layer to re-derive the reaching-binding algorithm from binding rows and activation intervals, which is precisely the source-side reimplementation the repository's design philosophy forbids.
  Rationale: an answer about an occurrence carries that occurrence's identity, or it is not an answer a correlated consumer can use.
  Date/Author: 2026-08-04, Fable 5.

Terms used below:

- "Facts" / "facts arena": `FileFacts` (`structural/facts.rs`) — per file, a pre-order array of `NormalizedNode { kind, range, parent, name, subtree_end }` plus role tables and a SHA-256 `ContentIdentity`. Descendants of node `n` are exactly `(n+1)..subtree_end(n)`; `is_ancestor` is O(1). Persisted under `STRUCTURAL_FACTS_SNAPSHOT_VERSION` (currently 2 after #1473).
- "AST identity": the pair `(ContentIdentity, arena node u32)`, published as a domain-separated digest (`occurrence_rows.rs::ast_id`). Structural captures, match roots, and occurrence rows all carry it; digest equality is the equijoin. Every new row family in this plan carries the same identity for its anchor node.
- "Occurrence row": `OccurrenceRow` (`occurrence_rows.rs:71-86`) — file, AST identity, range, role, class, namespace, enclosing declaration, spelling, and `OccurrenceTarget::{None, Resolved(Vec<CodeUnit>), Lexical(Box<LexicalDefinition>), Unresolved(DefinitionLookupStatus)}`. Reference-class rows are resolved in one batch per file at `occurrence_rows.rs:333-389`; line 379 zips rows with outcomes.
- "Definition resolution": `resolve_definition_batch_with_source_and_cancellation` (`get_definition/mod.rs:619`) — per request: lexical fast path (`resolve_lexical_binding`), then per-language dispatch (`mod.rs:1160-1324`), then outcome constructors `candidates_outcome` (`:1406`, sorts/dedups/keys candidates; one is `Resolved`, more is `Ambiguous`), `lexical_definition_outcome` (`:1627`), and the boundary gate `gated_boundary` (`:1680`). `DefinitionLookupStatus` is `Resolved | NoDefinition | UnresolvableImportBoundary | Ambiguous | UnsupportedLanguage | InvalidLocation | NotFound`.
- "Lexical grammar tables": `analyzer/lexical_definitions.rs` — per-language node-kind predicates (`is_lexical_scope`, `is_parameter_owner`, `is_binding_leaf`, `binding_container`, `is_local_declaration`, ...) covering all eleven languages. These are the seed vocabulary for scope and binder classification.
- "Capability spine": adapter support tables -> `QueryFeature` -> `CodeQueryDiagnosticCode` with `Incomplete` impact -> `CodeQueryResult::completion()` -> policy `PolicyIncompleteReason::CapabilityIncomplete` -> `PolicyRunCompletion` -> exit status. #1473 added per-axis honesty (`OccurrenceCompleteness::covers(role)`); this plan follows the same pattern for environment axes.
- "Assertion kind": `(analysis :type assertion :subject (rql ... :capture "N" ...) :asserts [(assert :id ... :at "N" ...)])` (`bifrost-policy`). Subject captures join to rows strictly by `ast_id`; any incomplete input makes the run `Inconclusive` with zero findings; violations render as one multi-location finding.

What exists that this plan builds on, and what does not exist (verified 2026-08-04 by survey; details in Surprises & Discoveries): no scope IDs or scope tree in any language; activation intervals only in Rust (`rust/lexical_scope.rs`) and Ruby, in incompatible private shapes; no reaching-binding computation anywhere (`OtherLocal` discards the winner); no precedence value, no rejected-candidate record, no typed rejection reason; imports modeled as `ImportInfo` rows with `StructuredImportPath` carrying unused positional data; wildcard ambiguity tracked only in Scala; no normalized source visibility; `NormalizedKind` had no `Block` (Milestone 1 added it) and still has no `Module`/`Package` kind; RQL exposes imports only as file-to-file edges (`imports-of`/`importers-of`).

What Milestone 5 must know. The rows an assert joins to are addressed as follows. A `binding` row's `ast_id` is the binder token's `(content_identity, arena node)` digest and is **optional**; a wildcard import and an adapter with no structured import path have none, so an assert whose `:at` names such a capture must be inconclusive rather than joined some other way. A `lexical_scope` row's `ast_id` is likewise optional, absent for exactly one scope per file. A `resolution_candidate` row's `ast_id` is the **reference's** identity, not the candidate's, and is mandatory -- so an assert about "the candidates considered for this occurrence" joins on the subject capture's `ast_id` directly, and several candidate rows share one. Within a reference, `ordinal` distinguishes them.

The three per-row fields a resolution assert must read before concluding anything: `tier` is `Option`, and `None` means unattributed -- a `:expect-tier` or `:forbid-tier` comparison over one must be `Inconclusive`, never a pass and never a violation. `trace_completeness` is `selection_only` for Python and JS/TS today, so an assert that depends on a rejection being present (a `:require-unique`, or anything reading `rejection_reason`) must be `Inconclusive` there. `candidate_kind` is one of `unit`, `lexical`, `binding`, `import_binder`, `external_route`, and only `unit` reaches a declaration, so an assert that wants a target must not treat the other four as "no target found".
