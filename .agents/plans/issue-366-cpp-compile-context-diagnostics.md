# Add compile-context-gated C++ unknown-symbol diagnostics

This ExecPlan is a living document. Maintain it according to `.agents/PLANS.md` from the repository root; every later change must keep this plan self-contained and add a note at the bottom describing why the plan changed.

## Purpose / Big Picture

Issue #366 adds an intentionally narrow C++ semantic diagnostic. A user who enables `unrecognizedSymbolDiagnostics` in the Language Server Protocol (LSP) will see an error for a clearly unknown C++ type only when Bifrost can load a matching `compile_commands.json` entry and prove that the type is not supplied by the project headers or a compiler configuration feature. A compilation database is the JSON file generated by CMake and similar tools that records the command used to compile each source file. It supplies the include roots and macro definitions that tree-sitter parsing alone cannot know.

The feature must prefer silence to an incorrect editor error. Missing, malformed, stale, ambiguous, or incomplete compilation context produces no C++ semantic diagnostics. Existing C++ navigation and include indexing remain unchanged.

## Surprises & Discoveries

- Observation: C++ currently has no semantic diagnostic collector at all. `CppAnalyzer` uses the default empty `IAnalyzer::semantic_diagnostics` implementation.
  Evidence: `src/analyzer/i_analyzer.rs` supplies the empty default and `src/analyzer/cpp/mod.rs` does not override it.

- Observation: the existing `unrecognizedSymbolDiagnostics` option already gates both pull and push LSP diagnostics after syntax error checks.
  Evidence: `src/lsp/handlers/diagnostic.rs` and `src/lsp/server.rs` pass the opt-in through to `MultiAnalyzer::semantic_diagnostics`.

- Observation: C++ include resolution is deliberately project-local and quoted-include-oriented. Treating it as a compiler model would change navigation behavior and create false certainty.
  Evidence: `src/analyzer/cpp/imports.rs` resolves indexed project files and leaves angle/system headers outside that model.

- Observation: an analyzer-backed `search_symbols` request with four broad diagnostic patterns and `include_tests: true, limit: 100` did not return in 41 seconds and was cancelled; an earlier mixed batch ran for about 90 seconds.
  Evidence: the exact request was `search_symbols(["semantic_diagnostics", "collect_.*semantic_diagnostics", "DiagnosticPublisher", "publish.*diagnostic"], include_tests=true, limit=100)`.

- Observation: compilation databases may use a relative `directory` in small fixtures even though production generators commonly use absolute directories.
  Evidence: resolving entry paths from the workspace root is required before `directory`, `file`, and relative flag paths can identify the project source consistently.

- Observation: an unparsed system or forced header can supply arbitrary declarations, so it invalidates the proof needed to report even an apparently simple missing type.
  Evidence: the collector returns no diagnostics when `-isystem` or `-include` context is present, and it accepts only a unique quoted project-header path through the configured roots.

## Decision Log

- Decision: make compile context diagnostics-only and do not extend `src/analyzer/cpp/imports.rs`.
  Rationale: the issue requires a trustworthy diagnostic gate, while the existing importer has a distinct project-navigation contract.
  Date/Author: 2026-07-27 / Codex.

- Decision: the first slice reports only an unqualified, non-dependent `type_identifier` in a proven type-reference position.
  Rationale: member names, functions, overloads, ADL, templates, macros, and conditional compilation require compiler semantics Bifrost does not yet model. A small, auditable positive surface satisfies the issue without claiming Clang-like coverage.
  Date/Author: 2026-07-27 / Codex.

- Decision: any uncertainty in compilation-database loading or the transitive project-header closure makes that translation unit non-emitting.
  Rationale: an editor false positive is worse than a missed diagnostic for this opt-in feature.
  Date/Author: 2026-07-27 / Codex.

- Decision: retain compile contexts behind a fresh `OnceLock` for each analyzer snapshot rather than read `compile_commands.json` during every C++ analyzer construction.
  Rationale: almost all C++ workspaces keep the global semantic diagnostic opt-in disabled. Lazy loading avoids an unrelated database read while snapshot replacement still invalidates stale context.
  Date/Author: 2026-07-27 / Codex.

- Decision: a macro defined through `-D` suppresses a same-named type-looking token, while in-source macro directives make the enclosing translation unit non-emitting.
  Rationale: tree-sitter cannot expand macros. Both choices preserve the no-false-positive requirement without pretending a text token is a compiler-resolved type.
  Date/Author: 2026-07-27 / Codex.

## Outcomes & Retrospective

The implementation loads a root `compile_commands.json` lazily and invalidates it with each analyzer snapshot. It reports `cpp_unrecognized_symbol` only for a simple unknown type in a syntactically clean source file whose matching compilation entry, include closure, and preprocessing state are proven. The direct collector tests cover missing context, a true positive, project headers, command-line macros, and template suppression. The LSP test proves default-off pull behavior plus enabled pull and save/publish output. `cargo fmt`, focused feature-enabled tests, `cargo clippy --all-targets --all-features -- -D warnings`, and the full `cargo test --features nlp,python` passed on 2026-07-27.

## Context and Orientation

`src/analyzer/i_analyzer.rs` defines the analyzer interface. `semantic_diagnostics` returns editor-facing semantic errors after the LSP has confirmed the source parses cleanly. `src/analyzer/multi_analyzer.rs` routes that call to the analyzer for the file's language.

`src/analyzer/cpp/mod.rs` owns `CppAnalyzer`, Bifrost's tree-sitter-based C and C++ analyzer. C and C++ currently share `Language::Cpp`; the parser intentionally provides syntax, not compiler preprocessing or type checking. `src/analyzer/cpp/imports.rs` uses project files to resolve quoted includes for navigation. It must not gain compiler include-path semantics in this work.

`src/lsp/handlers/diagnostic.rs` converts parser and semantic diagnostics to LSP ranges. `src/lsp/server.rs` supplies the global `unrecognizedSymbolDiagnostics` option for both explicit pull requests and published save diagnostics. These files should require no behavior change once `CppAnalyzer` implements the trait hook.

The new context module will treat a compilation-database entry as usable only when its `file` matches the requested source file after resolving relative paths against the entry `directory`; exactly one usable entry must exist. It will read `arguments` directly when present. If only a string `command` is present, it must be tokenized with a real shell-word parser, not `split_whitespace`, so quoted paths and definitions remain correct. The selected command is only a source of conservative flags: `-I`, `-iquote`, `-isystem`, forced includes, and `-D`. It is not a request to execute a compiler.

## Plan of Work

### Milestone 1: establish a fail-closed compilation context

Create `src/analyzer/cpp/compile_context.rs` and expose it from `src/analyzer/cpp/mod.rs`. Define a small immutable `CppCompileContext` owned by `CppAnalyzer` and indexed by normalized absolute `ProjectFile` path. It should retain the entry's project include roots, system include roots, forced-include paths, macro names, and a reason that an entry is non-emitting when Bifrost cannot prove enough context. Keep paths as `PathBuf` until a project-relative rendering boundary is required so Windows works correctly.

Load only the workspace-root `compile_commands.json`. Deserialize the standard entry fields `directory`, `file`, `arguments`, and `command`; do not implement an ad hoc JSON or shell parser. Resolve every usable source and include path relative to the command directory. Parse accepted compiler flag spellings as structured command tokens, including separate and attached forms where the compiler permits them. Treat malformed JSON, absent entries, duplicate matching entries, unreadable paths, and unsupported command shapes as no context rather than an error visible to the editor.

For a matching entry, retain the ordered quote/project roots, system roots, forced-include paths, and macro names that the collector will need. Do not change the existing `CppAnalyzer::import_statements` or `imports.rs` behavior. The collector milestone calculates the transitive project-header closure from parsed include nodes, because interpreting source text with ad hoc string scanning would be incorrect. Write focused context tests beside the module; fixture source and the JSON database belong in the temporary test project.

Milestone acceptance: a test can load a small database for `src/main.cpp`, see its project include root and `-D` macro name, and can distinguish a usable context from missing, malformed, unmatched, and ambiguous contexts without running a compiler.

### Milestone 2: collect only proven unknown type references

Create `src/analyzer/cpp/diagnostics.rs`. Follow the size limit, range conversion, source label, and diagnostic value conventions of the existing language collectors such as `src/analyzer/rust/diagnostics.rs`; define a C++ source label such as `bifrost-cpp` and a stable kind `cpp_unrecognized_symbol`.

Implement an iterative tree-sitter traversal. Use parsed preprocessor include nodes and the compile context's ordered roots to calculate the transitive project-header closure; if an include is missing, external or system, forced, macro-generated, or reaches a preprocessing form that cannot be evaluated, mark the translation unit non-emitting. If the source has a parse error, the source exceeds the collector budget, the file has no usable matching compile context, or the project-header closure is uncertain, return an empty vector. Otherwise identify only simple `type_identifier` nodes in true reference positions. Resolve against declarations in the source, declarations in every proven project header, locally declared aliases, and template parameters. Report an identifier only after all those sources reject it.

Explicitly return no diagnostic for declarations, function calls, member/field accesses, qualified names, labels, keywords, macros and preprocessor directives, any node within a conditional-preprocessing uncertainty boundary, template parameter and dependent constructs, standard-library-looking names, system or forced headers, and sites requiring receiver or overload inference. This means a known macro and a template parameter are suppressions, not declarations that happen to resolve. Add collector tests for each boundary and keep assertions behavior-focused: diagnostic kind, exact location, and absence/presence rather than implementation-specific traversal order.

Milestone acceptance: a matching tiny compilation database produces exactly one `cpp_unrecognized_symbol` for a clear missing type; a type supplied by a project `-I` header, an active `-D` macro, a template parameter, or an angle/system-looking reference produces none.

### Milestone 3: integrate with the analyzer and prove the LSP contract

Add `mod compile_context` and `mod diagnostics` in `src/analyzer/cpp/mod.rs`. Extend `CppAnalyzer` construction, cloning, `with_updated_inner`, and update paths to retain or reload the context consistently with the project snapshot. Implement `IAnalyzer::semantic_diagnostics` by delegating to the C++ collector. Do not add a new LSP preference: the existing global opt-in remains the only user setting.

Add a narrow test in `tests/bifrost_lsp_server.rs` that starts the server with a workspace containing the minimal compilation database. With `unrecognizedSymbolDiagnostics: true`, assert both pull diagnostics and the save/publish route contain one `cpp_unrecognized_symbol` at the expected range. With the setting absent or false, assert no C++ semantic diagnostic appears. Exercise an included project type in the same harness to prove the endpoint is not merely publishing all unresolved tree-sitter identifiers.

Update `docs/src/content/docs/lsp.md` and, if it describes the same setting, `docs/src/content/docs/vscode.md`. State that C++ diagnostics require a valid matching root `compile_commands.json`, are deliberately high-confidence and currently restricted to provable type references, and remain silent for system headers, macros/preprocessing, templates, dependent names, members, and calls.

Milestone acceptance: direct collector tests and LSP integration tests demonstrate default silence without compilation context, one true positive with it, no false positive for the required exclusions, and the documented boundary matches the implementation.

## Validation and Acceptance

Its compilation entry names `src/main.cpp`, supplies `-Iinclude` and a test macro, and its source references an undefined type exactly once.
