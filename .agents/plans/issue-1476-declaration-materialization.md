## Purpose / Big Picture

A workspace's declarations are not all written by hand. Ruby's `attr_accessor :name` materializes two methods that exist nowhere as `def` nodes; `alias_method :new_name, :old_name` materializes one; JavaScript's `export default { ... }` and `module.exports = { ... }` materialize export bindings with no declared name; Python's `@overload` stubs are declarations that must never run; C's `#define` creates a unit the type and call resolvers must honor; and a C++ export-annotation macro can wreck the parse so badly that the analyzer must *recover* the class declaration from an ERROR node. Bifrost's analyzers already model all of this internally — the seven mined commits in the issue inventory are the bug fixes that taught them to — but none of it is visible to RQL. A query cannot ask "which declarations in this file were generated, and by which macro invocation?", "does this `@overload` stub have an implementation?", "what does this file export, and is the default export anonymous?", or "is this declaration's existence contingent on a preprocessor configuration the analyzer does not know?". The provenance is computed at parse time and thrown away, or worse, never recorded at all: a Ruby generated accessor is a plain `CodeUnit` indistinguishable from a handwritten method.

The seven mined regressions share one shape: a materialized declaration (generated, exported, declaration-only, macro-backed, or recovery-shaped) was either missing, duplicated, wrongly runnable, or had a corrupted identity, and nothing queryable could have expressed the invariant "this literal generation site produces exactly these declarations, in this state". After this change, four things work that do not work today:

1. RQL can enumerate declaration state as typed rows: for the declarations of a file, each row states its origin (parsed from a declaration node, generated by a macro-like construct, or recovered from a broken parse), whether it is declaration-only (a signature that must not be treated as runnable behavior), and whether its presence is gated by a preprocessor configuration the analyzer has not evaluated. The same rows appear in canonical CodeQuery JSON.
2. RQL can enumerate generation sites and join them to their generated declaration sets: a `attr_accessor :a, :b` call is one row with a literal input classification and exactly four generated identities (two methods, two backing fields); `attr_accessor name.to_sym` is one row with a dynamic input classification and an explicitly unknown generated set — never an empty complete answer. Export declarations (named, default-named, default-anonymous, CommonJS root and member) are rows with their exported name and local target.
3. A declaration-only signature can be joined to its implementation: Python's `@overload` stubs link to the runnable `def` of the same callable, and a stub with no implementation is a representable, queryable absence.
4. The RQLP `assertion` analysis kind gains materialization asserts: a policy can pin the exact cardinality of a generation site's generated set, require or forbid a declaration state (an `@overload` stub reported as runnable behavior is the da26602 regression), and require implementation linkage. Dynamic generation sites and configuration-gated declarations yield `unreliable`/`Inconclusive`, never a clean pass or a silent miss.

Observability: after the final milestone, `cargo nextest run` shows materialization queries returning classified rows in the claimed languages (Ruby generation, Python declaration-state and linkage, JS/TS exports, C++ macro definitions/config gating); the policy CLI runs a generation-cardinality assertion that fails on a seeded missing-accessor fixture and passes on its near-miss; and dynamic-name fixtures in every claimed language report incomplete rather than empty.

## Surprises & Discoveries

Findings from the pre-plan survey (2026-08-05). Update this section as implementation proceeds.

- Observation: Ruby generated declarations carry no generation provenance at all. `visit_attr_macro` (`crates/bifrost-analysis/src/analyzer/ruby/declarations.rs:381`) creates one `Field` unit per literal argument (range: the whole `call` node) and, via `add_member_function` (`:451`), one or two `Function` units (range: the *argument* node), all through plain `CodeUnit::new_fq` — `synthetic` is `false`, and nothing records that the units came from a macro or which invocation produced them. `visit_alias_method` (`:429`) likewise. Dynamic arguments are silently skipped by `literal_symbol_or_string_name` returning `None` (`:397`) — the "dynamic generation happened here" fact is discarded at the same moment.
- Observation: the `synthetic` flag on `CodeUnit` (`crates/bifrost-core/src/analyzer/model.rs:1869`) is not "generated by a macro". Its setters are Kotlin data-class conveniences, C++ out-of-line/implicit members, and Scala synthetics — analyzer-invented identities, not source-backed generation. Reusing it as the generation marker would conflate two meanings; generation provenance needs its own record.
- Observation: `declaration_only` exists end-to-end for Python and nowhere else. `SignatureMetadata` carries it (`model.rs:306`), `python/declarations.rs:410` sets it from `PythonOverloadDecoratorBindings::decorates_as_overload` (`python/syntax.rs:95`, resolving `typing`/`typing_extensions` and their aliases from AST fields), it persists (payload epoch was bumped by da26602), and `code_quality/dead_code_smells.rs` consumes it. There is no stub-to-implementation link anywhere; dead-code analysis merely skips stubs.
- Observation: C++ `#define` units exist and are consulted. `visit_macro` (`cpp/declarations.rs:2922`) creates `CodeUnitType::Macro` units for `preproc_def`/`preproc_function_def`; commit adbc585 taught `get_definition/cpp.rs` to consult them. But `preproc_def` is not a structural fact — `cpp/structural.rs` maps only `preproc_include` — so a macro definition currently has no arena anchor for a row to join to.
- Observation: C++ parser recovery is elaborate and unrecorded. `cpp/declarations.rs` has a family of recovery functions (`displaced_exported_class_name` `:350`, `recover_fragmented_preprocessor_class` `:4183`, reparse-window machinery around `:439`) that materialize class/constructor units from ERROR-node shapes; the resulting units are indistinguishable from cleanly parsed ones. f7a2bb5's whole bug class — recovery selecting the wrong declarator — is invisible after the fact.
- Observation: preprocessor conditionals are parsed but never evaluated. `preproc_if`/`preproc_ifdef`/`preproc_else`/`preproc_elif` appear in `cpp/declarations.rs:969` only as traversal-transparent containers: declarations inside *all* branches are collected unconditionally. "Which branch is active" is not modeled anywhere, which is exactly the honest-uncertainty input the issue demands: a declaration inside a `preproc_if` is configuration-gated, and the analyzer must say so rather than pretend the declaration unconditionally exists.
- Observation: JS/TS default exports produce units at two shapes, both provenance-free. `visit_js_default_export_value` (`javascript/mod.rs:846`) routes function/class default exports to named-or-anonymous unit creation and object-literal defaults to `add_default_export_unit` (`js_ts/model.rs:61`); f5ee137 added CommonJS `module.exports = {...}` member units. `export default name` (re-export of an existing binding) deliberately creates no unit (`javascript/mod.rs:871`). None of these record an export form.
- Observation: the sibling substrate this plan reuses is exactly three files' pattern. Per-file derived rows with per-axis completeness: `structural/lexical_environment.rs` (1427 lines); vocabulary + declared support in core: `structural/resolution.rs` (489 lines, `labelled_enum!` shared from `occurrences.rs`); capability plumbing: `QueryFeature` in `structural/capabilities.rs` with per-adapter support hooks on `StructuralSpec`/`StructuralSearchProvider`. Current RQL `SCHEMA_VERSION` is 9 (`query/ir.rs:39`); the versions ladder in `query/schema.rs:28-38` ends at `RQL_RESOLUTION_SCHEMA_VERSION: u32 = 9`.
- Observation: Ruby's structural adapter maps `call` to `NormalizedKind::Call` (`ruby/structural.rs:20`), so a Ruby generation site (an `attr_accessor`/`alias_method` call) *is* already an arena fact and can anchor a row by AST identity without new fact kinds.

- Observation (M1): `labelled_enum!` derives serde with `rename_all = "snake_case"`, and the vocabulary test asserts serde output equals `label()`, so a label must be the exact serde snake_case of its variant name. `CommonJsRoot` is therefore labelled `common_js_root`, not the plan's sketched `commonjs_root`; anyone adding a variant must derive the label from the variant name, not from taste.
- Observation (M2): the store serializes side-table payloads with bincode, and bincode cannot deserialize serde's internally-tagged enums. `MaterializationRecordPayload` therefore uses serde's default externally-tagged representation; its JSON shape is irrelevant because it exists only inside the store.
- Observation (M2): not every store side table participates in the `blob_meta` count/integrity spine — `scala_exports` persists with no count column, no `PARSED_BLOB_INTEGRITY_CONDITION` subquery, and no `content_row_count` entry. Following that precedent for `materialization_records` avoided touching six count structures; the trade is that a partially-written record table is not detected by the post-write integrity check, exactly as for scala exports.
- Observation (M2): bumping the cache migration count re-keys the store file (`bifrost_cache.v15.db` after migration `0015`), so a schema addition forces a clean re-index by construction and no analyzer epoch-salt bump is needed. One migration test pinned the literal final version (`14`) and had to move to `CURRENT_MIGRATION_VERSION`; the mid-migration slice `[..13]` it also uses is index-based and stays valid.
  Evidence: `cache_db::tests::semantic_file_document_migration_rebuilds_only_semantic_index_rows` failed with `left: 15, right: 14` before the fix.
- Observation (M2): JavaScript and TypeScript are two complete visitor stacks, not one. `TypescriptAdapter` parses `.js` through the TS grammar and `visit_ts_export`, while `JavascriptAdapter` (`javascript/mod.rs`) owns the CommonJS `module.exports` machinery that f5ee137 added — the TS visitor has no CommonJS path at all. Export recording therefore lives in shared `js_ts/model.rs` helpers called from both dialects, and the producer tests must use the dialect-owning adapter (`JavascriptAdapter` for `.js`, `TypescriptAdapter` for `.ts`); the first test version used the TS adapter on `.js` and got zero CommonJS rows.
- Observation (M2): destructuring binders in `export const { a, b } = ...` introduce names the named-declarator walk does not enumerate; they get no export row rather than a guessed one. If Milestone 3 needs the honest gap surfaced, it becomes a per-file completeness reason there.
- Observation (M2): piping a gate command through `tail` replaces its exit code with tail's. Two "workspace clippy clean" checks in this plan's history were reporting tail's exit 0 while the log carried real errors — among them a facade-level test provider (`tests/suite_cross_language/structural_search_planner.rs`) missing the new `structural_supports_materialization_axis` trait method since Milestone 1. The M1 and M2-part-1 commit messages therefore over-claimed clippy cleanliness. Rule: capture gate output to a file and echo `$?`, never pipe the gate itself.
  Evidence: `cargo clippy ... | tail -3` reported exit 0; the same command redirected to a file reported exit 101 with E0046.
- Observation (M2): `FileState` literals exist in three places that the compiler only checks under `cfg(test)` for two of them (`parse_state` and `empty_file_state` in test modules). A plain `cargo build` after adding the field reported success while the test helpers were still stale; the first `cargo nextest` compile caught them.

## Decision Log

- Decision (M1): `materialization_support` is a required `StructuralSpec` method with no default, not the defaulted hook the first plan draft sketched, matching `occurrence_role_support` and `lexical_environment_support` verbatim ("deliberately has no default: the table is total, so a default would let a new adapter advertise support nobody implemented"). All eleven adapters state a table; seven state `NO_MATERIALIZATION_SUPPORT`.
  Rationale: convention consistency beats the marginal convenience of a default; the two sibling tables set the pattern and a third table that behaves differently would be a trap.
  Date/Author: 2026-08-05, Fable 5.

- Decision: the claimed language/axis matrix is deliberately non-uniform, unlike #1473/#1474's four-deep-adapter uniformity. Ruby claims generation sites and generated sets; Python claims declaration state (declaration-only) and implementation linkage; JS/TS claims export rows; C++ claims macro-definition rows, recovery provenance, and configuration gating. Nothing claims all axes. The mined commits are per-language by nature (attr_* is Ruby; @overload is Python; module.exports is JS; #define/recovery is C++), and forcing a uniform matrix would mean either inventing capabilities no producer computes or shrinking the slice to the empty intersection. The support table makes non-uniformity honest: every unclaimed (language, axis) pair reports unsupported, and queries over it report incomplete.
  Rationale: the capability spine exists precisely so partial rollout is sound; each axis ships where its producer already lives.
  Date/Author: 2026-08-05, Fable 5.
- Decision: generation provenance is recorded by the producers at declaration-collection time (typed records pushed into `ParsedFile` alongside the units, persisted with the store, epoch-bumped), not re-derived by the structural layer re-walking the tree. The structural derivation layer joins recorded provenance to arena facts by byte range within one `ContentIdentity`, exactly as the environment layer re-parses the snapshot's own source. Re-deriving would duplicate per-grammar macro-argument logic (`literal_symbol_or_string_name`, export-shape walks) in a second place, which is the drift the design philosophy forbids.
  Rationale: one grammar interpretation per fact; the analyzer that creates a generated unit is the only code that knows why it exists.
  Date/Author: 2026-08-05, Fable 5.
- Decision: dynamic generation is recorded as a first-class site record with no generated names, at the same producer points that today silently `continue` past non-literal arguments. The row's input classification (`literal` | `dynamic`) is the honesty carrier: a dynamic site makes the file's generated-set axis incomplete and any cardinality assert over it `Inconclusive`.
  Rationale: the issue's rule contract — unsupported dynamic names remain unknown — requires the *site* to be visible even when the names are not; discarding the site is how the silent-empty answer happens today.
  Date/Author: 2026-08-05, Fable 5.
- Decision: configuration gating is modeled as recorded preprocessor-conditional intervals per C++ file (recorded where `cpp/declarations.rs:969` already recognizes the container kinds), surfaced as a `config_gated` state on declaration rows whose declaration range falls inside one, and as an explicit "no active configuration is known" completeness reason on the axis. No preprocessor evaluation is built, and no attempt is made to decide branch activity.
  Rationale: the issue requires active configuration to be an explicit semantic input and absent configuration to report incomplete; recording the gate is cheap and honest, evaluating it is a compiler.
  Date/Author: 2026-08-05, Fable 5.
- Decision: implementation linkage (`implementation_of`) is derived in the materialization layer from the store — declaration-only signatures joined to the same callable identity's non-declaration-only unit in the same scope — not recorded by producers. Python's producer does not know the implementation at stub-collection time (it may not have been visited yet); the store after collection holds both ends. TS overload signatures are not claimed (the TS analyzer records no declaration-only metadata today); filed as a follow-up when Milestone 6 closes.
  Rationale: linkage is a join over collected facts, which is derivation-layer work by this plan's own producer/deriver split.
  Date/Author: 2026-08-05, Fable 5.
- Decision: schema version bumps 9 -> 10 (`RQL_MATERIALIZATION_SCHEMA_VERSION`) in Milestone 4, following the ladder discipline in `query/schema.rs`. New vocabulary enters only through the declarative registries (`query/schema.rs`, `bifrost-core/.../kinds.rs`) with parser, decoder, validator, hover, completion, TextMate, and tutorial coverage, per the repository's RQL-syntax-maintenance rules.
  Date/Author: 2026-08-05, Fable 5.
- Decision: materialization asserts extend the existing `assertion` analysis kind (as #1474's resolution asserts did), not a new kind, and every new assert family carries a required narrowing selector so an unrelated adapter gap cannot decide an unrelated verdict (the M5/M6 lesson recorded twice in the #1474 plan).
  Date/Author: 2026-08-05, Fable 5.

## Outcomes & Retrospective

(2026-08-05, all six milestones landed on `dave/github-issue-1476-c500c1`, draft PR #1637.) The issue's rule contract holds end to end: a supported literal generation form produces exactly the declarations promised (Ruby accessor/alias generation with exact cardinality, C++ `#define` units, JS/TS export materialization), dynamic names and configuration-dependent macros stay explicit unknown/incomplete outcomes, declaration-only signatures link to their implementations without becoming runnable behavior, no generated identity is reconstructed from call text (audited), and RQLP asserts generated-declaration cardinality and declaration state with multi-location evidence (site plus naming arguments). Deviations from the original sketch, all recorded in the decision log where they happened: `assert-implementation` was not built (the forward join suffices; the inverse listing is #1660), the claimed language/axis matrix is deliberately non-uniform, and the state-row join needed an `ast_id` anchor invented at M5 design time. The transferable lessons this plan adds to the sibling series: gate commands must never be piped through `tail` (a masked exit code hid a broken trait impl across two commits), bincode rejects internally-tagged serde enums, and the JS/TS dialect pair is two complete visitor stacks whose shared behavior must live in `js_ts/` helpers or it silently exists in only one dialect. Remaining follow-ups: #1657, #1658, #1659, #1660, plus the tutorial page case.

## Context and Orientation

Bifrost is a Rust workspace. `crates/bifrost-core` holds the analyzer model (`CodeUnit`, `SignatureMetadata`, `Range`) and the language-neutral structural vocabularies (`src/analyzer/structural/{kinds,occurrences,resolution}.rs`). `crates/bifrost-analysis` holds the per-language analyzers (`src/analyzer/<language>/`), the structural facts arena and query engine (`src/analyzer/structural/`), and the RQL/CodeQuery surfaces. "RQL" is the s-expression query language; "CodeQuery JSON" is its canonical JSON form; both decode into the IR in `structural/query/ir.rs`. "RQLP" is the policy layer whose `assertion` analysis kind evaluates asserts over rows joined to subject captures by AST identity. A "structural fact" is a row in the per-file pre-order arena (`structural/facts.rs`) with a `NormalizedKind` and byte range; an "AST identity" (`ast_id`) addresses one such row stably. Derived row families (occurrence rows from #1473, lexical-environment rows from #1474) are computed per file on demand, carry per-axis completeness, and are never persisted; only what identity requires lives in the arena.

The producers this plan exposes: Ruby generation in `ruby/declarations.rs` (`visit_attr_macro`, `visit_alias_method`, `add_member_function`, `literal_symbol_or_string_name`); Python declaration-only stubs in `python/declarations.rs:410` + `python/syntax.rs` (overload decorator bindings); JS/TS exports in `javascript/mod.rs` (`visit_js_export` and the default-export family) and `js_ts/model.rs` (`add_default_export_unit`), plus the CommonJS member units from f5ee137; C++ macros and recovery in `cpp/declarations.rs` (`visit_macro`, the recovery family around `:350`/`:4183`) with macro consultation in `usages/get_definition/cpp.rs`. The capability spine: `StructuralSpec` (per-adapter, `structural/extract.rs` neighborhood) exposes declared support tables; `StructuralSearchProvider` (`structural/provider.rs`) exposes them to the engine; `QueryFeature` (`structural/capabilities.rs`) turns an unsupported dependency into a typed diagnostic that RQLP maps to `unreliable`.

### Milestone 4 — RQL/JSON typed domain exposure, schema version 10

Following the #1474 M4 recipe end to end. The concrete design, fixed after reading the query surfaces (`query/ir.rs`, `query/schema.rs` form registry at `:990-1080`, `query/{sexp,json,decode,source}.rs`, `execution/plan.rs`, `search/mod.rs` + results):

Terminal domains: three new `QueryValueKind` variants — `GenerationSite => "generation_site"`, `Export => "export"`, `DeclarationState => "declaration_state"`. Implementation links need no kind of their own: `implementation-of` yields the `declaration` domain, and "stubs without implementations" is the existing set-difference composition.

Plan sources (sibling variants beside `Scopes`/`Bindings`, no `inside`-family fields, decoder rejects the combination naming the composable alternative): `generation-sites` (JSON `"generation_sites"`, IR `GenerationSiteSeed { filter: GenerationSiteFilter { kinds: Vec<GenerationKind>, inputs: Vec<GenerationInputClass> } }`, s-expr `(generation-sites [:kind ...] [:input ...])`) and `exports` (JSON `"exports"`, IR `ExportSeed { filter: ExportFilter { forms: Vec<ExportForm>, names: Vec<String> } }`, `(exports [:form ...] [:name ...])`; `:name` exact-match disjunction like binding `:name`).

Steps (each a `QueryStepOp` + form-registry entry + `QueryStep` variant, `since: 10`): `generates` (generation_site -> declaration_state rows of its generated units), `generated-by` (declaration|declaration_state -> generation_site rows), `declaration-state-of` (declaration -> declaration_state) carrying `DeclarationStateFilter { origins: Vec<DeclarationOrigin>, declaration_only: Option<bool>, config_gated: Option<bool> }` (`:origin ...`, `:declaration-only true/false`, `:config-gated true/false`), `implementation-of` (declaration_state|declaration -> declaration), `export-target` (export -> declaration).

Capability mapping (`QueryFeature::MaterializationAxis`): `generation-sites` -> GenerationSites; `generates`/`generated-by` -> GeneratedSets; `exports`/`export-target` -> Exports; `declaration-state-of` -> DeclarationState; `implementation-of` -> ImplementationLinkage. Configuration gating is a row field plus per-file completeness, never a separate query feature.

Diagnostics codes split by meaning: `MaterializationAxisUnsupported` (once per language), `MaterializationDerivationIncomplete` -> `PolicyIncompleteReason::CapabilityIncomplete`; `MaterializationRowBudgetExhausted` -> `PipelineRowBudget`.

Ladder: `RQL_MATERIALIZATION_SCHEMA_VERSION: u32 = 10`, `SCHEMA_VERSION` 9 -> 10. Filter fields go through the declarative field registries; where a JSON label would collide with an existing registry (the `ScopeFilterField` lesson), a new one-entry registry, never a renamed label. Typed dedup keys and detailed-evidence arms — grep `assert_detailed_terminal_identities` *before* the first run (the lesson recorded twice by the siblings). Then LSP hover/completion, REPL, policy plumbing, both TextMate grammars, and executable tutorials with a worked Ruby example whose expected output is real tool output. Acceptance: `tests/suite_cross_language/code_query_materialization.rs` runs classified rows in all claimed languages plus honest-incomplete runs for dynamic fixtures.

### Milestone 5 — RQLP materialization asserts

Two new families inside the existing `assertion` kind (`PolicyAssert` in `crates/bifrost-policy/src/definition.rs`), following the #1474 recipe (schema form registry entry with `OwnerApplicability::POLICY_ASSERTION`, source parse, canonical projection, evaluator arm, evidence, renderer):

`(assert-generation :id ID :at CAPTURE [:kind KIND] [:cardinality exactly|at-least|at-most N] [:forbid-dynamic true])` — the subject capture addresses the generation-site node (a Ruby macro call is an arena fact, so the join is the same `ast_id` equality every family uses). The evaluator adds a `generation-sites` seed query over the subject paths and joins site rows by `ast_id`. A literal site's `generated_count` is compared against the cardinality; a dynamic site is `Inconclusive` unless `:forbid-dynamic true` makes it a finding. Multi-location evidence needs the generated declarations' locations, so `CodeQueryGenerationSite.generated` changes from `Vec<String>` to structured entries carrying each generated unit's fq name plus its naming-argument range — the #1474 backlink lesson (a derived answer must carry the identity it answers for) applied at row-shape time instead of after a dead end.

`(assert-declaration-state :id ID :at CAPTURE [:origin ...] [:declaration-only true|false] [:config-gated true|false])` — the subject capture addresses a declaration node. To make the join an identity rather than a cross-producer coordinate comparison, `DeclarationStateRow` (and its public row) gains an optional `ast_id` anchor derived in the materialization layer by exact byte-range match of the unit's primary declaration range against the facts arena (`fact_at_range`, the same inverse-of-extraction argument as the site anchor). A state row without an anchor (generated units, range-adjusted declarations) cannot be addressed by a capture, so the assert is inapplicable there — silence, not inconclusive — and a captured declaration with no joined state row under a claimed axis is `Inconclusive`.

Deliberately not built: `assert-implementation`. Linkage presence/absence is already expressible on the query surface as `implementation-of` composed with set difference, and an assert family would duplicate that with no additional evidence; recorded here as the decision instead of a milestone item.

Acceptance: `tests/suite_bench_policy/policy_materialization_assertions.rs` — a cardinality assert fails on a seeded missing-accessor fixture, passes on the near-miss, reports `Inconclusive` on the dynamic fixture without `:forbid-dynamic`, and reports a finding with it.
